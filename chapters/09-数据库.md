## 数据库

### 数据库系统概述

#### 数据库系统的基本概念

- 数据（Data）：描述事物的符号记录
- 数据库（DB）：长期存储在计算机内、有组织、可共享的大量数据的集合
- 数据库管理系统（DBMS）：位于用户与操作系统之间的一层数据管理软件，是数据库系统的核心
  - 主要功能：数据定义、数据操纵、数据库的运行管理、数据库的建立与维护
- 数据库系统（DBS）：由数据库、DBMS、应用程序、数据库管理员（DBA）和用户组成
- 数据管理技术的发展：人工管理阶段 -> 文件系统阶段 -> 数据库系统阶段

#### 数据库系统的三级模式结构

| 模式 | 别名 | 面向对象 | 特点 |
| ---- | ---- | ---- | ---- |
| 外模式 | 子模式、用户模式 | 应用程序、用户 | 一个数据库可有多个外模式，每个外模式对应一个用户视图 |
| 模式 | 逻辑模式、概念模式 | 全局逻辑结构 | 一个数据库只有一个模式，是所有用户的公共数据视图 |
| 内模式 | 存储模式 | 物理存储结构 | 一个数据库只有一个内模式，描述数据的物理存储与存取方法 |

两级映像与数据独立性：

- 外模式/模式映像：当模式改变时，通过修改映像使外模式不变，保证数据的**逻辑独立性**
- 模式/内模式映像：当内模式改变时，通过修改映像使模式不变，保证数据的**物理独立性**

### 数据模型

#### 概念模型（ER模型）

- 实体（Entity）：客观存在并可相互区别的事物
- 属性（Attribute）：实体所具有的某一特性，属性有取值（域）
- 联系（Relationship）：实体之间的相互关联
  - 一对一（1:1）
  - 一对多（1:n）
  - 多对多（m:n）
- ER图表示：实体用**矩形**、属性用**椭圆**、联系用**菱形**表示

#### 常用的逻辑模型

| 模型 | 特点 | 优缺点 |
| ---- | ---- | ---- |
| 层次模型 | 树形结构，有且只有一个根结点，结点间具有父子关系 | 结构清晰，但只能表示1:n联系 |
| 网状模型 | 图结构，允许一个以上结点无父结点 | 可表示m:n联系，但结构复杂，用户掌握困难 |
| 关系模型 | 二维表结构，数据结构简单，集合运算 | 关系规范化，数据冗余度低，独立性高 |

关系模型是目前使用最广泛的模型，也是软考重点考查对象。

#### 关系模型的基本概念

- 关系（Relation）：一张二维表
- 元组（Tuple）：表中的一行
- 属性（Attribute）：表中的一列，每列有一个属性名
- 域（Domain）：属性的取值范围
- 分量：元组中某个属性的值
- 关系模式：对关系的描述，记为 $R(A_1, A_2, ..., A_n)$

#### 关系的键

- 超键（Super Key）：能唯一标识元组的属性或属性组合
- 候选键（Candidate Key）：**不含多余属性**的超键（最小超键）
- 主键（Primary Key）：从候选键中选定的一个作为主键
- 外键（Foreign Key）：若某属性（组）不是本关系的主键，但它是另一关系的主键，则该属性（组）为本关系的外键

#### 关系的完整性约束

1. 实体完整性：主键取值不能为空
2. 参照完整性：外键取值要么为空，要么等于被参照关系中某元组的主键值
3. 用户定义完整性：针对具体应用的约束（如年龄大于0，性别只能取"男"/"女"）

### 关系代数

#### 关系代数的运算分类

- 集合运算（并、交、差、笛卡尔积）
- 专门的关系运算（选择、投影、连接、除）

#### 传统集合运算

| 运算 | 符号 | 说明 | 元组数 |
| ---- | ---- | ---- | ---- |
| 并 | $R∪S$ | 属于R或属于S的元组 | $\|R\|+\|S\|-\|R∩S\|$ |
| 交 | $R∩S$ | 同时属于R和S的元组 | $\|R\|-\|R-S\|$ |
| 差 | $R-S$ | 属于R但不属于S的元组 | $\|R\|-\|R∩S\|$ |
| 笛卡尔积 | $R×S$ | R的元组与S的元组所有组合 | $\|R\|×\|S\|$ |

注：并、交、差运算要求 R 与 S **同结构**（属性个数相同、对应属性域相容）。

#### 专门的关系运算

| 运算 | 符号 | 说明 | 对应SQL |
| ---- | ---- | ---- | ---- |
| 选择（Selection） | $σ_F(R)$ | 从R中选取满足条件F的**行**（水平切片） | WHERE |
| 投影（Projection） | $π_A(R)$ | 从R中选取列A组成新关系（垂直切片），结果去掉重复元组 | SELECT 列 |
| 连接（Join） | $R⋈S$ | 从笛卡尔积中选取满足连接条件的元组 | JOIN |
| 除（Division） | $R÷S$ | 求包含S中所有属性值的R的元组 | NOT EXISTS 嵌套 |

连接运算分类：

- θ连接（条件连接）：$R⋈_{AθB}S$，θ为比较运算符（=,>,<,...）
- 等值连接：θ为"="的连接
- 自然连接：在等值连接基础上**去掉重复属性列**的连接（最常用）

除运算示例：$R÷S$ 的结果为 R 中包含了 S 全部属性值的那些属性。

#### 表达式与SQL的关系

数据库中，**表达式通常指"关系代数表达式"**，SQL 是它的**具体实现/等价转换**。二者关系是：**关系代数表达式的每一步操作都对应一条 SQL 子句**，可以相互转换。

| 关系代数 | SQL |
| --- | --- |
| π (投影 projection) | SELECT 列名 |
| σ (选择 selection) | WHERE 条件 |
| ⋈ (连接 join) | JOIN / FROM + ON 条件 |
| × (笛卡尔积) | CROSS JOIN |
| ∪ (并) | UNION |
| − (差) | EXCEPT/MINUS |
| ÷ (除) | NOT EXISTS 嵌套查询 |

核心考点：能写出某关系代数表达式的等价 SQL，或反之；以及"任何 SQL 查询的本质都是基于关系代数运算"。

记忆口诀：**"π 对 SELECT，σ 对 WHERE，⋈ 对 JOIN，∪ 对 UNION"**

### SQL语言

#### SQL的分类

| 类别 | 全称 | 常用语句 |
| ---- | ---- | ---- |
| DDL | 数据定义语言 | CREATE、DROP、ALTER |
| DML | 数据操纵语言 | SELECT、INSERT、UPDATE、DELETE |
| DCL | 数据控制语言 | GRANT、REVOKE |

#### 数据定义（DDL）

- 建库/建表：`CREATE TABLE <表名> (<列名> <类型> [约束], ...)`
- 删表：`DROP TABLE <表名>`
- 改表：`ALTER TABLE <表名> ADD/ALTER/DROP COLUMN ...`
- 常用约束：PRIMARY KEY（主键）、FOREIGN KEY（外键）、NOT NULL、UNIQUE、CHECK

#### 数据查询（SELECT）

基本语法：`SELECT [DISTINCT] <列> FROM <表> [WHERE <条件>] [GROUP BY <列> [HAVING <条件>]] [ORDER BY <列> [ASC|DESC]]`

- WHERE 与 HAVING 的区别：
  - WHERE 作用于**分组之前**，不能使用聚合函数
  - HAVING 作用于**分组之后**，可以使用聚合函数
- 聚合函数：COUNT（计数）、SUM（求和）、AVG（平均）、MAX、MIN
- 模糊查询：`LIKE`，通配符 `%`（任意多个字符）、`_`（任意一个字符）
- 排序：`ORDER BY` 升序 ASC、降序 DESC

连接查询：

- 内连接：`INNER JOIN ... ON`，只返回满足条件的行
- 左外连接：`LEFT JOIN ... ON`，返回左表全部行，右表无匹配则为NULL
- 右外连接：`RIGHT JOIN ... ON`，返回右表全部行
- 全外连接：`FULL JOIN ... ON`，返回两表全部行

嵌套查询（子查询）：

- `IN`：判断是否在子查询结果中
- `EXISTS / NOT EXISTS`：判断子查询是否有结果（对应除运算）
- `ANY / SOME`：与子查询中的任一值比较
- `ALL`：与子查询中的所有值比较

#### 视图（VIEW）

- 视图是从一个或多个基本表导出的**虚表**，只存储定义不存储数据
- 优点：简化查询、提供数据独立性、安全保密性（用户只能访问视图内的数据）
- 创建：`CREATE VIEW <视图名> AS <SELECT语句>`

#### 数据控制（DCL）

- 授权：`GRANT <权限> ON <对象> TO <用户> [WITH GRANT OPTION]`
- 收回：`REVOKE <权限> ON <对象> FROM <用户>`

### 关系数据库规范化理论

#### 函数依赖

设 $R(U)$，X、Y 为属性集 U 的子集，若 X 的每个值唯一决定 Y 的值，则称 X **函数决定** Y，记作 $X→Y$。

- 平凡函数依赖：$X→Y$ 且 $Y⊆X$（恒成立，无意义）
- 非平凡函数依赖：$X→Y$ 且 $Y⊄X$
- 完全函数依赖：$X→Y$ 且 X 的任何真子集都不能决定 Y
- 部分函数依赖：$X→Y$ 且 X 的某个真子集能决定 Y
- 传递函数依赖：$X→Y$，$Y→Z$，且 $Y⊄X$，则 $X→Z$

#### 候选键的求解（闭包法）

求属性集 X 的闭包 $X^+$：反复将可推导出的属性加入，直到不变。

- 候选键：$X^+ = U$ 且无冗余属性（X 的所有真子集的闭包≠U）
- 求解步骤：
  1. 找出所有能决定其它属性的属性（最可能成为键）
  2. 求该属性集闭包，若等于 U 则它是超键
  3. 去掉冗余属性，使之为候选键
- 规律：
  - 只出现在函数依赖**右边**的属性，一定不是候选键
  - 只出现在函数依赖**左边**的属性，一定属于每个候选键

#### 范式（NF）

| 范式 | 要求 | 解决的冗余 |
| ---- | ---- | ---- |
| 1NF | 关系每个分量都是不可再分的数据项（最基本的范式） | — |
| 2NF | 满足1NF，且**非主属性完全函数依赖**于候选键（消除非主属性对键的部分函数依赖） | 部分依赖造成的插入、删除异常 |
| 3NF | 满足2NF，且**非主属性不传递依赖**于候选键（消除传递函数依赖） | 传递依赖造成的数据冗余 |
| BCNF | 满足3NF，且每个**决定因素都包含候选键**（消除主属性对键的部分/传递依赖） | 主属性之间的冗余 |
| 4NF | 消除非平凡且非函数依赖的多值依赖 | 多值依赖造成的冗余 |

规范化过程：1NF -> 2NF（消除部分依赖）-> 3NF（消除传递依赖）-> BCNF（消除主属性部分依赖）-> 4NF（消除多值依赖）

#### 模式分解

分解必须满足的两个条件：

1. **无损连接分解**：分解后的关系自然连接能还原原关系，无数据丢失
2. **保持函数依赖**：分解后各关系的函数依赖集合等价于原依赖集

分解注意：

- 若分解得到的关系模式都是 **3NF/BCNF**，则分解通常是无损且保持函数依赖的
- 将关系模式分解为3NF且保持函数依赖：对每个函数依赖的**最小依赖集**，每个依赖单独建一个模式
- 判断无损连接：构造初始表格法，看能否通过函数依赖将某一行填满

### 事务与并发控制

#### 事务及其特性（ACID）

事务是用户定义的一个数据库操作序列，是数据库系统并发控制和恢复的基本单位。

| 特性 | 含义 | 破坏因素 |
| ---- | ---- | ---- |
| 原子性（Atomicity） | 事务要么全部执行，要么全部不执行 | 事务故障 |
| 一致性（Consistency） | 事务执行前后数据库完整性保持一致 | 并发问题、故障 |
| 隔离性（Isolation） | 一个事务的执行不被其它事务干扰 | 并发问题 |
| 持久性（Durability） | 事务一旦提交，其修改就永久保存 | 系统故障、介质故障 |

事务结束语句：`COMMIT`（提交）、`ROLLBACK`（回滚）

#### 并发控制产生的三个问题

1. **丢失更新**：两个事务同时修改同一数据，后提交的覆盖先提交的
2. **不可重复读**：一个事务内两次读同一数据，结果不同（另一事务修改了该数据）
3. **读脏数据（脏读）**：一个事务读到另一事务**未提交**的修改数据

#### 封锁协议

- 排他锁（X锁，写锁）：事务T对数据加X锁后，T可读写，其它事务既不能加X锁也不能加S锁，直到T释放
- 共享锁（S锁，读锁）：事务T对数据加S锁后，T可读不可写，其它事务可加S锁但不能加X锁

| 封锁协议 | 解决的问题 |
| ---- | ---- |
| 一级封锁协议 | 事务修改数据前先加X锁直至结束。可防止**丢失更新** |
| 二级封锁协议 | 一级 + 读数据前加S锁，读完即释放。还可防止**读脏数据** |
| 三级封锁协议 | 一级 + 读数据前加S锁直至事务结束。还可防止**不可重复读** |

两段锁协议（2PL）：所有事务分为扩展阶段（加锁）和收缩阶段（解锁），**加锁和解锁不能交叉**，保证并发调度的可串行化。

#### 死锁

- 定义：两个或多个事务互相等待对方释放锁而形成的僵局
- 死锁的四个必要条件：互斥、保持和等待、不可剥夺、循环等待
- 解决办法：预防（一次封锁法、顺序封锁法）、检测和解除（超时法、等待图法）

### 数据库恢复

#### 故障类型

| 故障 | 说明 | 恢复方法 |
| ---- | ---- | ---- |
| 事务故障 | 事务内部错误（如除零、死锁回滚） | 反向扫描日志，执行UNDO |
| 系统故障 | 断电、宕机等，非物理损坏 | 正向扫描日志，REDO未提交事务 + UNDO未完成事务 |
| 介质故障 | 磁盘损坏、物理数据丢失 | 装入备份 + REDO |

#### 恢复技术

- 数据转储（备份）：静态转储、动态转储；海量转储、增量转储
- 日志文件：记录事务对数据库的更新操作
- 恢复策略：
  - UNDO（撤销）：将未提交事务的修改恢复到原值
  - REDO（重做）：将已提交但未写入磁盘的事务重新执行

### 数据库安全

- 用户标识与鉴别：口令、指纹、证书等身份验证
- 存取控制：自主存取控制（DAC，GRANT/REVOKE授权）、强制存取控制（MAC）
- 视图机制：通过视图隐藏机密数据
- 审计：记录用户对数据库的所有操作，用于事后追踪
- 数据加密：存储加密、传输加密

### 数据库设计

#### 设计的步骤（六阶段）

1. **需求分析**：调查了解用户需求，输出数据流图（DFD）、数据字典（DD）
2. **概念结构设计**：设计ER图（不考虑具体DBMS）
3. **逻辑结构设计**：将ER图转换为关系模式（针对具体DBMS优化）
4. **物理结构设计**：确定存取方法和存储结构（索引、聚簇等）
5. **数据库实施**：建立数据库、加载数据、试运行
6. **数据库运行和维护**：性能监控、调整、转储与恢复

#### ER图转换为关系模式

- 每个**实体**转换为一个关系模式，实体的属性为关系的属性，实体的键为关系的键
- 每个**联系**转换规则：
  - 1:1联系：可以并入任意一端的实体关系模式中，或单独建一个关系模式
  - 1:n联系：将联系并入**n端**实体，或在1端加入n端主键
  - m:n联系：**必须单独建立**一个关系模式，其属性为两端实体的主键 + 联系自身的属性

转换原则速记：**"一对一任一方，一对多并入多，多对多必建新表"**

#### 数据字典

数据字典是系统中各类数据描述的集合，包括：数据项、数据结构、数据流、数据存储、处理过程五个部分。
